# F31h — стартовая резервная копия в фоне

Этап подготовлен от `49df097`, вместе с F31g и исправлением watchdog `03d626b`.
F31 остаётся **OPEN**: Windows CI для этого этапа и проверка реального
Windows Rescue/HDD/VHDX ещё не выполнены.

## Поведение

`Program` подключает владельца экземпляра через `instance.Attach`, затем только
ставит одно событие на постоянный UI dispatcher. Проверка начинается после
первого dispatch message pump, а не в конструкторе tray context и не перед
`Application.Run`. Чтение `VERSION`, перечисление копий, manifest snapshot,
проверка состава/контрольных сумм и необходимое копирование выполняются в worker.

Сканирование и создание используют общий gate writers. Существующая подходящая
базовая копия принимается только после проверки shared SHA-256 index. Если она
готова, новый каталог не создаётся: интерфейс сообщает «Стартовая копия уже есть
и проверена. Новая копия не создавалась». Это не результат ручного копирования.
На каждый старт допускается одна попытка; ошибки, отмена и повторное открытие
состояния не создают циклов повторных проверок. Таймеры не запускают baseline.

Стартовая операция не открывает окно автоматически. Русский статус виден на
главной странице, в диагностике и в пункте «Состояние копии» меню резервных копий.
Пункт меню и ссылка на главной открывают состояние и отмену текущей операции.
При ошибке данные не заменяются; состояние остаётся доступно, журнал содержит
санитизированную ошибку. После устранения причины владелец может отдельно создать
ручную копию. Программный manual request во время startup открывает текущий
baseline progress и получает его task: очереди и ложного manual success нет.

До фактического завершения worker команды создания ручной копии, восстановления,
очистки и обновления ждут. Настройки и остановка подключений доступны. После
проверки уже существующей копии ограничения сразу снимаются. Нормальный выход
и обслуживание отменяют worker и ждут его фактического завершения до 3 секунд.
Если накопитель удерживает операцию дольше, выход отклоняется; ProGo сохраняет
владение worker. `Dispose` не ждёт диск и не применяет поздние UI результаты.
Отмена проверяется при перечислении каталогов, между manifest/metadata reads,
в inventory/валидации и между блоками настоящего копирования и SHA-256.
Непрерываемый вызов ОС заканчивается в worker; token не объявляет его завершённым.

Состав архивов, отсутствие импорта DPAPI на другой ПК, PIN/формат vault, политика
retention, граница принятия полной копии и restore scopes не изменяются. VPS,
`authorized_keys`, SSH-agent и системные настройки startup backup не меняет.

## Оставшиеся интеграции

### Минимальный размер окон

Статус копии в диагностике добавляет строку внутри вертикально прокручиваемой
таблицы. Исходный минимум окна `790 × 610` и четыре кнопки неподвижного footer
сохранены. При отсутствии callback главное окно не создаёт пустую скрытую ссылку
копии: её неиспользованные bounds раньше нарушали проверку неперекрывающихся
строк. Длинный живой статус остаётся в ограниченной по ширине native stack.

`DesktopStartupBackupLayoutTests.cs` проверяет настоящие окна, размеры строк,
полный текст, вертикальную прокрутку, отсутствие горизонтальной, кнопки footer,
закрытие с отменой трёх измерений и settling без нового UI dispatch. Три PNG
попадают в существующий `desktop-shots` artifact. Компиляция и native выполнение
этой layout-поправки **NOT_CHECKED** до Windows CI; F16 и F31 остаются **OPEN**.

`StartRestore` всё ещё читает список копий и metadata перед chooser синхронно;
предпросмотр retention и подтверждённая очистка в `CleanupBackups` тоже остаются
синхронными. Подготовка выбранной restore copy уже выполняется отдельно в worker.
Другие ранние startup операции (`EnsureDirectories`, миграция ярлыков и загрузка
settings) этим этапом не профилируются и не объявляются быстрыми на HDD. Требуются
их отдельная проверка и реальные замеры; весь F31 этим этапом не закрывается.
